# Асинхронный микросервис аудита безопасности Docker-образов

## Назначение и возможности
Сервис принимает запросы на проверку Docker-образов, ставит задачу в очередь и асинхронно сканирует образ на уязвимости с помощью Trivy, сохраняя историю, сводку и отчёты в PostgreSQL. Полный результат сканирования доступен по `GET /scans/{id}`.

## Сценарий работы
1. Клиент отправляет `POST /scans` с именем образа на публичный IP `vm-api` (`139.100.194.107:8000`).
2. API создаёт запись со статусом `queued` в PostgreSQL (таблица `scan_jobs`, поле `image_name`) и кладёт задачу в очередь Redis (`trivy_scan_jobs`).
3. Воркер (`trivy-worker`) на `vm-worker` забирает задачу из Redis, запускает сканирование образа через Trivy внутри контейнера, обновляет статус на `running`, затем на `completed` (или `failed`) и сохраняет сводку и отчёт в PostgreSQL.
4. Клиент забирает статус и полный результат сканирования по `GET /scans/{id}` (или смотрит запись в таблице `scan_jobs`).

## Компоненты облачной инфраструктуры
- **`vm-api` (Ubuntu, публичный IP `139.100.194.107`):** API-сервер (порт `8000`) с привязанной группой безопасности `sg-vm-api`.
- **`vm-worker` (Ubuntu, приватный IP в подсети `192.168.0.0/24`):** воркер `trivy-worker` в Docker-контейнере, запускаемый через `docker compose`, с привязанной группой безопасности `sg-vm-worker`.
- **Приватная сеть (`192.168.0.0/24`):** связывает `vm-api`, `vm-worker` и управляемые сервисы БД и очереди.
- **Managed PostgreSQL (`audit_db`):** хранение истории задач, статусов и результатов сканирования в таблице `scan_jobs`.
- **Managed Redis:** брокер очереди задач (`trivy_scan_jobs`) между API и воркером.

## Архитектура и взаимодействие компонентов
`Client (Internet) -> [139.100.194.107:8000] vm-api -> Redis Queue (trivy_scan_jobs) -> vm-worker (Private IP, Trivy Worker) -> PostgreSQL (audit_db.scan_jobs)`

## Адрес сервиса и проверка доступности
- Базовый URL по публичному IP: `http://139.100.194.107:8000`
- Проверка доступности сервиса: `GET http://139.100.194.107:8000/health` (ожидаемый ответ: `{"status":"ok"}`)

## Конфигурация, запуск и эксплуатация
Переменные окружения хранятся в общем файле `.env` на узлах (например, `/root/docker-image-audit-service/.env`):
- параметры подключения к Managed PostgreSQL (`audit_db`) и Managed Redis (`trivy_scan_jobs`).

### Инициализация базы данных
Перед первым запуском сервисов на чистой Managed PostgreSQL необходимо применить скрипт инициализации схемы (например, `sql/init.sql`) с загруженными переменными из `.env`:
```bash
set -a
source /root/docker-image-audit-service/.env
set +a
psql "$DATABASE_URL" -f /root/docker-image-audit-service/sql/init.sql
```
*(Если вместо единой строки `DATABASE_URL` используются отдельные переменные подключения, передайте хост, порт, имя базы `audit_db` и пользователя `psql`.)*

### Запуск и проверка API на `vm-api`
Сервис API запускается на `vm-api` (порт `8000`) через Docker Compose с политикой автоперезапуска при сбоях (`restart: unless-stopped`):
```bash
cd /root/docker-image-audit-service/infra/vm-api
docker compose --env-file /root/docker-image-audit-service/.env up -d --build
docker compose --env-file /root/docker-image-audit-service/.env ps
docker compose --env-file /root/docker-image-audit-service/.env logs --tail=50
```

### Запуск и проверка воркера на `vm-worker`
Запуск выполняется из каталога `infra/vm-worker`:
```bash
cd /root/docker-image-audit-service/infra/vm-worker
docker compose --env-file /root/docker-image-audit-service/.env up -d --build
docker compose --env-file /root/docker-image-audit-service/.env ps
docker compose --env-file /root/docker-image-audit-service/.env logs --tail=50
```

### Выход `vm-worker` в интернет и работа с реестрами / базами Trivy
Несмотря на отсутствие публичного IP у `vm-worker`, воркеру требуется исходящий доступ к реестрам контейнеров и источникам баз уязвимостей Trivy (по `HTTPS / 443` через SNAT/NAT-шлюз провайдера), а также доступ к Managed Redis и Managed PostgreSQL. В группе безопасности `sg-vm-worker` разрешены необходимые исходящие подключения и закрыты внешние входящие порты.

### Отказоустойчивость очереди и очистка диска на `vm-worker`
- **Перезапуск воркера во время задачи:** если `vm-worker` перезагружается во время активного сканирования, задача может остаться в статусе `running` (либо не завершиться корректно, если очередь не использует надёжную схему подтверждения обработки/повторов с контролем зависших задач). Для промышленной эксплуатации требуется контроль зависших задач в `running` и политика ретраев/повторной постановки в очередь.
- **Очистка образов и кэша Trivy:** скачанные образы и кэш баз Trivy занимают место на диске `vm-worker`. Необходимо регулярно очищать неиспользуемые образы и кэш (например, через `docker image prune` / очистку кэша Trivy по расписанию или после выполнения задач), чтобы диск не переполнялся.

## Проверка работы
1. Проверить доступность API:
   ```bash
   curl -s http://139.100.194.107:8000/health
   ```
2. Поставить образ на сканирование (например, `alpine:3.19` или `debian:bookworm-slim`):
   ```bash
   curl -s -X POST http://139.100.194.107:8000/scans \
     -H "Content-Type: application/json" \
     -d '{"image":"alpine:3.19"}'
   ```
3. Проверить статус и результат по `id`:
   ```bash
   curl -s http://139.100.194.107:8000/scans/<SCAN_ID>
   ```
4. Проверить запись в PostgreSQL (таблица `scan_jobs` с колонкой `image_name`):
   ```sql
   SELECT id, image_name, status, created_at FROM scan_jobs ORDER BY created_at DESC LIMIT 10;
   ```

## Безопасность, IAM и модель совместной ответственности
- **Принцип наименьших привилегий (текущее состояние и целевое развитие):** в текущем стенде каталоги проекта (`/root/docker-image-audit-service`) и часть операций показаны от имени `root`, а API доступен по `http://139.100.194.107:8000` без включённой авторизации и HTTPS. В качестве развития по принципу наименьших привилегий и защиты периметра предполагается:
  - запуск сервисов и контейнеров под отдельными непривилегированными пользователями/аккаунтами и ограничение прав доступа к файлам/ключам;
  - выдача учётным записям в PostgreSQL только необходимых прав на базу `audit_db` и таблицу `scan_jobs`;
- **Сетевая изоляция и Security Groups:** к сетевым портам виртуальных машин привязаны отдельные группы безопасности:
  - **`sg-vm-api`** (привязана к `vm-api`): разрешает входящий TCP-трафик на порт `8000` (API) и порт `22` (SSH) из `0.0.0.0/0`, а также исходящий трафик в приватную сеть к Managed Redis и Managed PostgreSQL.
  - **`sg-vm-worker`** (привязана к `vm-worker`): запрещает все внешние входящие подключения, разрешает входящий SSH (`22/TCP`) только из приватной подсети (`192.168.0.0/24`) и исходящий трафик к Managed Redis, Managed PostgreSQL и во внешнюю сеть (`443/TCP`) для скачивания Docker-образов и баз уязвимостей Trivy.
- **Хранение секретов:** файл `.env` не попадает в систему контроля версий (добавлен в `.gitignore`), а доступ к нему на серверах ограничен правами файловой системы (`chmod 600`).
- **Модель совместной ответственности:**
  - **Облачный провайдер отвечает за:** физическую инфраструктуру, гипервизор и хосты виртуальных машин, базовую сетевую плоскость (включая маршрутизацию/NAT на уровне облака) и доступность управляемых сервисов (Managed PostgreSQL и Managed Redis) на уровне платформы.
  - **Владелец сервиса отвечает за:** конфигурацию приложения и `.env`, актуальность и безопасность Docker-образов (включая устранение уязвимостей, найденных Trivy), корректные правила Security Groups, разграничение доступов и защиту публичного эндпоинта API.
